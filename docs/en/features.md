# Features

aantje adds a view to the Activity Bar that shows the structure of a DuckLake catalog and the first rows of its tables, plus a SQL editor that runs any SQL against the lake. This page lists what it does and where it stops.

The explorer is read-only. The tree reads the `ducklake_*` metadata tables with read-only SQL, so browsing needs no DuckLake extension. Reading data (grid, notebook, view columns) uses a private, read-only DuckDB with the DuckLake extension. The SQL editor has its own writable sessions ([Security](security.md)).

## Explorer

- **Connections** to DuckLake catalogs stored in PostgreSQL, SQLite or DuckDB, or served by a DuckDB server over Quack (token in the secret storage, TLS with a pinned certificate): add, edit, remove, test, connect, disconnect ([Connections](connections.md)).
- **Azure DuckLake**: **Create Azure DuckLake...** deploys a PostgreSQL server (catalog) and an ADLS Gen2 account (data files) from a Bicep template, gives you the storage role and adds the lake as a connection, signed in once with your Microsoft account. **Finish Creating Azure DuckLake...** picks up a deployment whose wait broke off, **Import Azure DuckLake...** adds a lake from the output of a portal deployment, **Delete Azure DuckLake...** removes one that aantje created ([Azure DuckLake](azure-lake.md)).
- **AWS DuckLake**: **Create AWS DuckLake...** creates PostgreSQL on Amazon RDS (catalog) and an S3 bucket (data files) in a VPC of its own from one CloudFormation template, with an AWS profile of your configuration (IAM Identity Center included): it checks the names, quotas and your permissions, shows the change set, cleans up a failed creation and adds the lake as a connection. **Finish Creating AWS DuckLake...** picks up a creation whose wait broke off, **Import AWS DuckLake...** adds a stack created by hand, **Allow My IP** updates the address of the stack, **Delete AWS DuckLake...** deletes the database of a lake that aantje created (with or without a final snapshot), empties the bucket and deletes the stack. PostgreSQL signs in with a generated password or with IAM database authentication (a token of your AWS profile for every connection, no password stored; also in Add Connection for any RDS server). A PostgreSQL server on RDS is checked against the certificate authorities of RDS, which aantje ships ([AWS DuckLake](aws-lake.md)).
- **Sync to Iceberg**: **Sync to Iceberg...** on a connection, a schema or a table writes the tables at one snapshot into an Iceberg REST catalog (Polaris, Lakekeeper) that you define once as a target, under the namespace and name you choose, one Iceberg commit per table, partitioned like the lake where Iceberg can, with the origin as table properties, and remembers each copy; a later sync appends what the lake inserted and replaces what it changed, and a table the lake changed since shows `Iceberg: n behind` ([Sync to Iceberg](iceberg.md)).
- **Tree** of schemas with the folders Tables, Views and Macros. A table has Columns (STRUCT, LIST and MAP expand into nested fields), Partitioning, Sort Order and Tags when present, and the leaves **Statistics** and **History** that open reports. The tree shows no counts; rows and size are in the tooltip and the statistics report ([Tree](tree.md)).
- **Snapshots** folder: the newest snapshots with time, author, commit message and changed objects. **Show Catalog at this Snapshot** and **Show Latest Snapshot** change what the whole tree shows ([Snapshots, search and status bar](snapshot-search-status.md)).
- **Files** folder: the storage of the lake (local disk, S3, S3-compatible, Azure, OneLake) one level at a time, without the lake's data files, signed in with the storage of the connection. **Script as Import into New Table...** and **Script as Insert into Existing Table...** write the script for a CSV, Parquet, JSON or Excel file, or for the files of one kind in a folder or in its subfolders, such as Hive partitions (`year=2026/month=09/`), whose folder names become columns that you name; nothing runs until you run it ([Files](files.md)).
- **Columns of views.** DuckLake stores no columns for a view, so DuckDB resolves them. That runs the SQL stored in the catalog, so aantje asks once per connection whether you trust it. The SQL of a view is in its tooltip.
- **Tooltips**: rows, size and comment of a table, comment of a view, parameters of a macro, type of a column.
- **Copy** the qualified name of a schema, table, view or column, and the DDL of a table or view.
- **Edit Comment...** on a table, a view or a column of a table opens the `COMMENT ON` statement in a SQL document; nothing runs until you run it ([DDL generation](ddl.md#edit-comment)).
- **Catalog search** for tables, views and columns (nested fields too) in all schemas, with a jump to the hit.
- **Execute Macro...** on a macro asks for its overload and parameters (SQL, an empty input keeps the default) and opens the call in a SQL document; nothing runs until you run it ([DDL generation](ddl.md#execute-macro)).
- **Filter...** on a connection, a schema or its folders Tables, Views and Macros shows only the objects whose name holds a text or matches a pattern with `*` and `?`; the filter stays per connection in the workspace, and **Clear Filter** removes it ([Tree](tree.md#filter)).
- **Status bar** item with the connection, DuckLake version and snapshot.

## Scripts

- **Script as** SELECT, CREATE, ALTER or DROP on every node that has a script, and INSERT on a table, opens it in a new SQL editor of the connection. **Script as INSERT with Data...** on a table or view writes a `CREATE TABLE` and `INSERT` statements with all its rows; above 100,000 rows or 2 MB it asks first and can save the script to a file ([DDL generation](ddl.md#script-as-insert-with-data)). Nothing runs until you run it. Scripts that create or alter contain the matching DROP as a comment ([DDL generation](ddl.md)). A query with a row limit ends in `LIMIT $limit{1000}`, so its run asks for the limit with 1000 proposed ([Parameters](sql-editor.md#parameters)).
- **Generate Scripts...** on an open connection or a schema scripts its tables, views and macros in an order that works: one SQL document, or one file per object in a folder for Git ([DDL generation](ddl.md#generate-scripts)).
- **Rename...** in Script as on a table, a view or a column of a table writes the rename together with `CREATE OR REPLACE` of every view and macro that names it, changed only at DuckDB's tokens and in one transaction; a column rename follows the column through the views at any depth, what cannot be changed safely is listed at the top, and a table synced to Iceberg gets a note on what its next sync does. Nothing runs until you run it ([DDL generation](ddl.md#rename)).
- **Schema Compare...** compares two tables or two schemas, also across schemas and connections: a diff editor or a Markdown report of what differs, and **Script as Update**, the statements that make the target like the source ([Schema Compare](compare.md)).
- **Data Compare...** compares the rows of two tables, also across schemas and connections, by key columns or whole rows: the rows only in one table and the rows that differ in the grid, exact counts, and **Script as Update**, a `MERGE` (or a replace) that makes the rows of the target like those of the source; across two connections the session of the script attaches the source ([Data Compare](compare.md#data-compare)).
- **Maintenance** on a connection and a table: Checkpoint, Merge Adjacent Files, Rewrite Data Files, Flush Inlined Data, Expire Snapshots, Clean Up Old Files, Delete Orphaned Files, Set Option. Each opens the DuckLake call; what destroys data starts with a dry run and the real call is commented out ([Maintenance scripts](maintenance.md)).

## Time travel

- **Query at Snapshot...** opens the first rows, a notebook or a SQL editor at any snapshot at which the table existed.
- **Compare Table at Two Snapshots...** shows the `CREATE TABLE` of two snapshots in a diff editor. **Compare Snapshots...** writes a Markdown report of changed tables, views and columns.
- **Show Changes...** shows the rows inserted, updated and deleted between two snapshots in a grid. **Show Rows Changed** does so for one snapshot ([Time travel](time-travel.md)).
- **Restore Table to Snapshot...** writes the script that gives a table the rows of an earlier snapshot back and keeps its id. **Restore Dropped Object...** on a schema writes the script that creates a dropped table, view or macro again. Nothing runs until you run the script ([Time travel](time-travel.md#restore-table-to-snapshot)).

## Data

- **Select Top 1000 Rows** shows the first rows of a table or view in a grid: DuckDB types, NULL marked, sort by header, filter row, columns of 200 pixels, copies in the context menu of the cells (also as Markdown) and **Export as File** as CSV, JSON or Markdown, at the snapshot the tree shows ([Data access](data-access.md), [Data grid](grid.md)). **Column Statistics** shows above each column of the whole table, computed by DuckDB: a histogram, the type, the NULLs, minimum, maximum and average or distinct, first and last value, or the counts of true and false ([The statistics of the columns](grid.md#the-statistics-of-the-columns)).
- **Export...** writes all rows of a table or view at the snapshot the tree shows to a CSV, Parquet, JSON or Markdown file, in the same read-only engine; a CSV file holds every value as it is, a Markdown table of more than 10,000 rows is asked about first ([Data access](data-access.md#export)).
- **Create Notebook...** opens a self-contained Jupyter notebook that attaches the lake read-only at the same snapshot. It contains no password ([Notebooks](notebooks.md)).
- **S3 data.** Set `aantje.s3.endpoint` and the key with **Set S3 Credentials...** for Parquet files on S3 or MinIO.

## Reports

The **Reports** submenu opens panels with one look: the logo of aantje before the title, and charts, cards and selections in the colours of aantje, built from the navy, orange and slate of the logo ([The colours of aantje](branding.md#the-colours-of-aantje)). All but the Iceberg report have **Open as Markdown**, and where data can change, **Refresh** ([Reports](reports.md)).

- **Show Details** on a connection, a schema or its Tables folder: the tables, views and macros in one sortable list with rows, size, data files, small and delete files, inlined rows, partitioning, sort order, last change, creation and dependencies; filter, choose columns, **Copy** for a spreadsheet, and the actions of a row ([Details](details.md)).
- **Statistics** (table): files, size, rows, small files, file size histogram, null share and range of columns, partition evenness, growth ([Statistics](statistics.md)).
- **Snapshot Report**: swimlane chart and a table of pages of the newest 500 snapshots, in two tabs, with filters and actions ([Snapshot report](snapshot-report.md)).
- **Schema History** (table): the columns at two snapshots and what changed between them, and every change of one column ([Schema History](schema-history.md)).
- **Growth**: rows, size or files over the snapshots, for the lake or a table, as a chart and as a table of pages of every snapshot ([Growth report](growth-report.md)).
- **Activity**: key figures and tabs for the commits per day, the changes by kind, the authors, the most changed tables and the changes of each table; the snapshots one by one are the Snapshot Report's ([Activity report](activity-report.md)).
- **Inactive Tables**: the tables of a lake or a schema without a change for 30, 90, 180, 365 or any number of days, with their last change, rows, size, files and comment, a page at a time with a filter box, and Show in Tree, Show Statistics and Dependencies as icons on each. A snapshot that only maintained files is no change. Reads are not recorded by DuckLake; the last read is a hint from your local Query History ([Inactive Tables](inactive-tables.md)).
- **Storage Report**: data path, largest tables, small files, files waiting for deletion ([Storage report](storage-report.md)).
- **Properties**: the facts of the catalog and every row of `ducklake_metadata`.
- **Maintenance Advisor**: what maintenance would do, measured with the DuckLake dry runs, ranked by impact, effort and risk. Nothing is executed ([Maintenance Advisor](advisor.md)).
- **Dependencies**: what uses an object and what it uses, in tabs of tables and graphs. The lake and a schema: a table of their objects, a page at a time, with the actions of each object in its row, and a graph. An object: the tables **Depends on** and **Used by** to a depth, a graph with everything connected to it, and for a table or view the column lineage as tables and as a graph: where each column of a view comes from through any depth of views (direct, derived, filter, join, group), and which view columns use a column. **Show Column Lineage** on a column opens it for that column; **Visualize** frames what is connected to an object ([Dependencies](dependencies.md)).
- **Check Health** and **Check Table Health**: the catalog, the connection and the object store, with an optional deep check of Parquet footers. **Check Health at Snapshot...** checks the state of an older snapshot, and **Find Last Good Snapshot...** walks back to the newest snapshot at which the checks pass, with the actions that go back to it. Rows with ids that no snapshot ever had are findings too. Nothing runs without your action ([Health check](health-check.md)).
- **Inspect Data Files...** (a table) and **Inspect Parquet File** (a file of the Files folder): the footer of a Parquet file: row groups with the ranges of a column and how much they overlap, encodings, compression, statistics, field ids and the DuckLake columns they map to, key/value metadata and a probe of the bloom filters. Inspect Data Files... picks one file, and the panel switches between the files of the pick in a drop-down. Only the footer is read, with the storage sign-in of the connection; an encrypted lake's files are not opened ([Parquet inspector](parquet-inspector.md)).
- **Suggest Partitioning...** (a table): partition and bucket columns from the filters of your local Query History, read with DuckDB's parser, and from the data measured read-only (distinct values, partitions per unit of time, the largest partition): each candidate with its partitions, files per partition and their size, reasons and risks, or a sort order instead; **Open Script** writes a dry run, then the partitioning and the rewrite commented out ([Suggest Partitioning](partitioning.md)).
- **Catalog Dashboard**: the database that holds the catalog: its size, the size and rows of its tables and of the inlined data (a page at a time, with a filter box), and for PostgreSQL the dead rows and the last vacuum and analyze, with a VACUUM (ANALYZE) script for a PostgreSQL client. Statistics views only ([Catalog Dashboard](catalog-dashboard.md)).

## SQL editor

**New Query** on a connected connection or any node below it opens a SQL document bound to that connection: with the SELECT of a table or view, empty on any other node. The editor completes names, shows hover and signature help, marks syntax errors and warns of the tables, views and columns that the lake does not have, with a quick fix to the nearest name ([SQL IntelliSense](sql-intellisense.md)). **Run Query** (`F5`), **Run Statement at Cursor** (`Ctrl+Enter`) and **Cancel Query** (`Shift+F5`) run it. **Run to File...** writes the whole result of a statement that only reads to a CSV, Parquet, JSON or Markdown file ([Run to File](sql-editor.md#run-to-file)). A script can leave values open as `$name` (bound, never pasted into the SQL), with a default where it is used as `$name{default}` (`LIMIT $limit{1000}`), and names as `{{name}}` (replaced as a quoted identifier, literal, checked number or date), declared in its header; a run asks for them in one dialog and remembers the last values per document ([Parameters](sql-editor.md#parameters)). A `$name` where a name goes (`FROM $table`) gets a warning that says to write `{{table}}`, since a name cannot be bound. **Column Statistics** shows above each column of a result its figures for the whole result, computed by DuckDB in the session ([The statistics of the columns](grid.md#the-statistics-of-the-columns)). Each result has a chart in the tab after its own, with its columns mapped to the axes, in the colours of aantje, and **Aggregate in DuckDB** draws all rows of a result that has more than were loaded ([The chart of a result](grid.md#the-chart-of-a-result)). Each editor has its own session, and results open in a panel below that stays with the editor: it follows it, comes forward with it and closes with it, and **Hide Results** (`Ctrl+Alt+R`) gives the query the whole height. The editor runs any SQL with the rights of the connection's credentials. A profile can open its sessions read-only (`readOnly`), and **Toggle Read-only Session** switches one editor; a Quack connection has no such switch, its server decides what the token may do. A run that commits a change asks once for a commit message of its snapshots, empty by default ([Commit messages](sql-editor.md#commit-messages)). An `UPDATE` or `DELETE` without `WHERE` stops the run and asks first, with the number of rows of its table ([UPDATE and DELETE without WHERE](sql-editor.md#update-and-delete-without-where)). After a statement that changed the catalog, the tree reads the connection again ([SQL editor](sql-editor.md), [SQL session](sql-session.md)). The folder **Query History** below a connection lists the last statements you ran on it, with time, duration, rows and status; a double-click opens one in a new query. **Set as Favorite** keeps a statement in the folder **Favorites** at its top, where it stays when the history rotates or is cleared, under a name of your own if you like (unique per connection) ([Query History](sql-editor.md#query-history)). After **Statistics** and **Analysis** the tab **Tips** lists what would make the statement faster: a sort order for a selective scan, whether the run read from the storage or from DuckDB's cache, spilling to disk, maintenance of a scanned table and the columns a scan reads, each with a script to open where one applies ([Performance tips](sql-editor.md#performance-tips)).

## Templates

**Templates** in the `...` menu of the catalogs view (or **aantje: Templates**) opens a page with the logo and a search field, as on a search engine start page: it finds templates by name, description, tags and SQL text while you type, and shows the ones you used most and last as tiles, four in a row, and below them the templates created last, your own mixed with those of aantje and of your folders (by the day in their header). **Browse** lists all templates by name in the width of the tiles, with their description, tags and source and their actions as icon buttons, narrowed by the search, a tag and a source, a page at a time. **Use** opens a template as a new SQL document of a connection, its `{{name}}` placeholders filled in through the dialog of the parameters and its `$name` values left for the run; nothing runs. aantje ships DuckLake templates (a partitioned table from Parquet files, a `MERGE` upsert, the rows changed between two snapshots, time travel by version and by time, adding Parquet files, a commit message, flushing inlined data, expiring snapshots and cleaning up files as dry runs, restoring a table) and generic ones of plain SQL for any table (duplicate keys, removing duplicates as a dry run with the delete of only the duplicate rows commented out, orphaned rows, comparing two tables, missing days, data freshness, top N per group, running totals, a pivot, outliers by z-score), each run against a real lake in the tests. Your own templates come from **Duplicate**, **Save Selection as Template...** in the SQL editor and **Import...** of `.sql` files or a `.json` bundle; you edit, export and delete them, and `aantje.templates.folders` lists the templates of folders (a team's Git repository) read-only. A template with a password, key or token in its header, defaults or statements is refused ([Templates](templates.md)).

## AI assistants

aantje runs an MCP server on `127.0.0.1` (setting `aantje.mcp.enabled`), so that Copilot and Claude Code in VS Code can read the lakes that the explorer has connected: **list_connections**, **list_objects**, **describe_object** (columns, comments, layout, the SQL of a view or macro, the lineage of the columns of a view, dependencies at any depth), **table_statistics** and **maintenance_advice** from the catalog; **explain**, **explain_analyze** (Analysis) and **profile** (Statistics, both with the performance tips) on one statement that reads, in a read-only session of their own; **sample_rows** only when `aantje.mcp.maxRows` allows rows; **open_sql**, which opens SQL for you and runs nothing; **iceberg_status** and **request_iceberg_sync**, which opens the question of a sync to Iceberg in VS Code for you to confirm; three prompts (_Why is this slow?_, _Optimize this query_, _Extend this view_) and notes on DuckDB and DuckLake SQL. None of aantje's tools writes by itself, connects a connection or touches the session of a SQL editor (an assistant's own tools, such as a shell, are outside aantje). The server tells the assistant to answer questions about the lakes with these tools rather than from files of the workspace. Copilot finds the server by itself; **Add MCP Server to Claude Code** adds it to Claude Code for your user ([MCP server](mcp.md)).

## Known limits

- Row counts cover data files only, minus deleted rows. Inlined rows are not counted. They are exact at the latest snapshot and can be off at an older one after compaction.
- A SQLite catalog is read from a copy taken at connect. Refresh to see newer commits. A catalog with an uncheckpointed write-ahead log is refused.
- A DuckDB file held open for writing by another process cannot be opened, and while aantje is connected the file is locked against writers. A writable SQL session locks it exclusively, so aantje disconnects the explorer first and leaves it disconnected. PostgreSQL and a Quack server suit several clients.
- Quack is experimental in DuckDB 2.0.0. A Quack catalog cannot be attached read-only, so the server must refuse writes; a server restart ends open SQL sessions (the explorer attaches again).
- Schemas nested in schemas (specification 1.1) are shown flat.
- **Copy DDL** and **Script as CREATE** write DuckDB syntax. A view stored in another dialect stays in that dialect.
- A view that DuckDB cannot bind (a dropped table) shows the error instead of columns.
- The grid shows at most 1000 rows of a table. Sorting and filtering work on those rows only. There is no paging. **Export...** writes all rows to a file.
- Reading data needs the data files. For S3, set the endpoint and credentials, or the `AWS_*` variables. A relative data path is found only if the extension host's working directory happens to be right.
- Nested values are shown as JSON text. BIGINT and DECIMAL are shown as exact text.
- **Copy Row** and **Copy All** neutralise formulas (a leading `'` on text starting with `=`, `+`, `-`, `@`, tab or CR); **Copy Cell** keeps the exact value. Every CSV file that aantje writes (the export of the grid, **Export...**, **Run to File...**) holds the values unchanged, so a spreadsheet may read a text that starts with `=` as a formula. The CSV is UTF-8 without a byte order mark.
- An Azure lake is read with an Entra token that the DuckDB `azure` extension does not renew; a long SQL session replaces it every ten minutes. Nothing of the Azure feature has been run against a real subscription yet ([Azure DuckLake](azure-lake.md#what-is-verified-and-what-is-not)).
- A notebook is generated once; later changes do not reach an open notebook. The preview grid, and the connection and session of a SQL document, are not restored after a restart.
- The SQL editor keeps at most `aantje.sql.maxRows` rows of a result; sorting and filtering work on the loaded rows. A statement such as `WITH ... INSERT` does not count as a change, so use Refresh.
