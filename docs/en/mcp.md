# MCP server

aantje runs a [Model Context Protocol](https://modelcontextprotocol.io) server in the extension host, so that an AI assistant in VS Code (GitHub Copilot, Claude Code) can read the lakes that the explorer has connected: the objects, their columns and dependencies, the statistics of a table, the advice of the Maintenance Advisor, the plans and profiles of statements that read, and the state of the syncs to Iceberg. The assistant can then say why a query or view is slow and write SQL that binds on the first try. None of aantje's tools writes by itself, connects a connection or touches the session of a SQL editor; SQL that changes something the assistant opens for you with `open_sql`, and you run it, and a sync to Iceberg it asks you for in VS Code, where you confirm it. This holds for aantje's tools only: what an assistant does with its other tools, such as a shell or the files of the workspace, and with the credentials its environment holds, is up to the assistant, its permissions and the rights of those credentials ([Security](security.md#the-mcp-server)). The code is in `src/mcp/`.

The server runs while `aantje.mcp.enabled` is on (the default, machine scope). Switching it off stops the server and its sessions and removes it from VS Code's list of MCP servers.

## How assistants reach it

The server listens on `127.0.0.1` on a free port with a token that is new at every start, speaking Streamable HTTP (MCP protocol 2025-11-25, a session per client). Clients never type the port or the token:

- **VS Code's own MCP clients (Copilot):** aantje registers the server through `contributes.mcpServerDefinitionProviders` (id `aantje.mcp`, label `aantje`) with its URL and the token header. VS Code lists it without setup and learns of every restart.
- **Claude Code:** **aantje: Add MCP Server to Claude Code** writes the entry `aantje` in Claude Code's user scope with the CLI that the Claude Code extension brings (`claude mcp add-json --scope user`), else `claude` on the path. The entry starts a small stdio bridge, `aantje-mcp-bridge.js`, with the Node of the editor (Electron as Node on the desktop, Node itself in code-server). aantje copies the bridge at every start to `mcp/` in its global storage, so that the entry survives updates. Start a new Claude Code session after adding it.

Every window of VS Code runs its own server. Each writes a file with its URL, token and workspace folders to `mcp/windows/<pid>.json` in the global storage (folder only for the user, file mode `600`) and removes it when it closes. The bridge takes the window whose workspace holds the directory Claude Code runs in (the deepest when workspaces nest), else the only window; when none or several fit, it says so on its error output. So with two windows open, Claude Code in each reaches the aantje of its own window.

A hard stop (a container that is rebuilt, a killed extension host) leaves the file of its window behind, and its process number may belong to another process after a restart. So a file counts only when its server answers: the bridge asks `GET /alive` with the token of the file, and the server answers `204` with the number of its process (header `x-aantje-pid`), which must be the one of the file; the bridge waits at most 1.5 seconds. When a window starts its server, it removes the files of other windows that are unreadable, whose process has ended, or whose port answers as something else; a server that is only slow to answer keeps its file.

Once, when the Claude Code extension is installed and its CLI says that it has no server `aantje`, aantje offers **Add to Claude Code** in a message after its view was first shown. Nothing is written unless you press the button; the message does not come again.

### What the server tells the assistant

With the answer to `initialize` the server sends instructions, which Claude Code and other clients put into the context of the assistant: that aantje's tools read the connected lakes as they are now, that questions about them are better answered with these tools than with files of the workspace such as notebooks, which can be out of date, to start with `list_connections`, to read the notes before writing SQL, that changes go through `open_sql` to the user, and that `request_iceberg_sync` asks the user to confirm a sync to Iceberg. They are a hint to the assistant, not a guard: an assistant that is asked to read the notebooks still can.

## Tools that read the catalog

These tools read what the explorer has open, with its reader. They are marked read-only (`readOnlyHint`), declare an output schema and return structured content plus the same JSON as text. A connection is named as **list_connections** names it (the spelling of the name first, else ignoring case). Names of schemas and objects follow DuckDB: the exact spelling first, else ignoring the case of A to Z.

| Tool                 | Input                                           | Returns                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `list_connections`   | none                                            | Name, kind of catalog (`postgres`, `sqlite`, `duckdb`, `quack`) and whether the explorer has it connected. Never a host, path, user, password, token or key.                                                                                                                                                                                                                                                                   |
| `list_objects`       | `connection`, optional `schema`                 | The schemas with their comment, their tables (comment, rows, whether the row count is approximate, files, size), views (comment) and macros (scalar or table), each by name.                                                                                                                                                                                                                                                   |
| `describe_object`    | `connection`, `schema`, `name`, optional `kind` | A table: its columns with DuckDB SQL types (`DECIMAL(10,2)`, `STRUCT(...)`), nullability, defaults and comments, rows, files, size, partitioning, sort order and tags. A view: its SQL, dialect and column aliases. A macro: its overloads with parameters and SQL. For all: the [dependencies](dependencies.md), see below. `kind` (`table`, `view`, `macro`) is needed only when a table or view and a macro share the name. |
| `table_statistics`   | `connection`, `schema`, `table`                 | What the [Statistics](statistics.md) report shows: rows, data and delete files and their bytes, the largest file, small files, the file size histogram, the partitions (the largest, the rest counted, how evenly filled), the null ratio, minimum and maximum of each column (DuckLake type names), and the growth over the snapshots.                                                                                        |
| `maintenance_advice` | `connection`, optional `schema`                 | What the [Maintenance Advisor](advisor.md) reads: the policy of the lake, the dry runs of Expire Snapshots, Clean Up Old Files and Delete Orphaned Files, the files waiting for deletion, and the recommendations with the name of aantje's maintenance script, the table, a title, an explanation, figures, and impact, effort and risk.                                                                                      |

The dependencies of an object list what it reads or calls (`uses`) and what reads or calls it (`usedBy`), at any depth (`depth` 1 is next to it) and with the kind of edge (`reads`, `calls`); then the names in its SQL that the lake does not have (`brokenReferences`) and what the analysis could not follow (`unresolved`), as the Dependencies report does.

`list_objects`, `describe_object` and `table_statistics` read at the snapshot of the explorer: while it follows the newest snapshot, the newest one that its reader sees when the call starts (also when the lake changed after the last refresh), else the one pinned with **Show Catalog at this Snapshot**. A SQLite catalog is read from the copy taken at connect, as everywhere in aantje. Every result names its `snapshot`. `maintenance_advice` reads the newest snapshot, as the Maintenance Advisor does; it lists the data path of the lake for the orphaned files and runs the dry runs in a private read-only DuckDB, like the report, so on a large store it takes a while. It uses the storage sign-in of the connection and never shows a sign-in.

## Tools that hand a statement to DuckDB

| Tool              | Input               | Returns                                                                                                                                                                                                                                                                           |
| ----------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `explain`         | `connection`, `sql` | DuckDB's `EXPLAIN (FORMAT JSON)`: the plan, or DuckDB's error when the statement does not bind. `EXPLAIN` runs nothing, so this is the check that a proposed query binds; for a view the assistant explains `SELECT * FROM schema.view`, for a change of a view its new `SELECT`. |
| `explain_analyze` | `connection`, `sql` | **Analysis** of the SQL editor: `EXPLAIN (ANALYZE, FORMAT JSON)` runs the statement to its end; the plan with time and rows per operator, and the [performance tips](sql-editor.md#performance-tips).                                                                             |
| `profile`         | `connection`, `sql` | **Statistics** of the SQL editor: the statement with DuckDB's profiler; the profile (time, CPU time, bytes read, peak memory, time and rows per operator) and the performance tips. No rows; like the editor it reads at most `aantje.sql.maxRows` rows of the result.            |
| `sample_rows`     | `connection`, `sql` | The first rows of the statement, at most `aantje.mcp.maxRows`, with the names and DuckDB types of the columns. Offered only while that setting is above 0; it is 0 by default, so no tool returns rows.                                                                           |
| `open_sql`        | `connection`, `sql` | Opens the SQL as a new, unsaved SQL document bound to the connection, for you to check and run. Runs nothing; the connection need not be connected.                                                                                                                               |

Before a statement goes to DuckDB:

- **One statement that reads.** The text is cut into statements on DuckDB's tokens, as the SQL editor cuts a script; a text with more than one is refused. Each of the four tools takes only a statement that the tokens show to read (`SELECT`, `FROM`, `WITH ... SELECT`, `VALUES`, `SUMMARIZE`, `DESCRIBE`, `SHOW`), the check of the CodeLens that fails closed. A statement with SQL in a string, such as `query('...')`, counts as no such statement.
- **Views.** When the views of the connection are not trusted yet and the statement may bind one (a name in it, quoted or not, or a word in a string, equals the name of a view or macro of the lake), aantje asks in VS Code as Select Top 1000 Rows does. A decline is the error of the tool, and nothing runs.
- **Its own session.** Each connection has one session of the MCP tools: a DuckDB that attaches the lake read-only (a DuckDB catalog file is not locked against other readers), with the access of the SQL editor but never a sign-in. It opens with the first call, takes one call at a time, and closes after ten idle minutes, when the explorer disconnects the connection, when the profile changes and when the server stops. It is never the session of a SQL editor, so your transactions and `SET`s stay as they are. Statistics changes the profiler settings of that session around the statement and puts them back, as in the editor; a session that refuses that is closed.
- **Time limit and cancel.** `aantje.queryTimeoutSeconds` stops a statement; so does a cancel of the client (`notifications/cancelled`), which interrupts DuckDB.

A plan, a profile or the rows of an answer hold at most 256 KB of text; a larger plan or profile comes as its first 256 KB, marked `truncated`, and rows are left out from the end. DuckDB's errors come back as they are, with the secrets of the connection masked.

A Quack connection runs the statement in the local DuckDB that attaches the Quack catalog, as the SQL editor does; Analysis and Statistics profile that DuckDB, and the tips read no Parquet footers there.

## Tools for the syncs to Iceberg

| Tool                   | Input                                                     | Returns                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iceberg_status`       | `connection`, `target` (optional)                         | The state of the [syncs to Iceberg](iceberg.md) of the lake, checked now as the row in the tree is: per target whether it is in sync, the newest snapshot of the lake, and per synced table its problems (`lake-newer`, `iceberg-ahead`, `iceberg-replaced`, `iceberg-missing`, `lake-dropped`, `not-checked`), the snapshot of its last sync and how many snapshots it is behind; and the tables of the lake that a synced lake or schema does not have yet. Read-only; it asks the Iceberg catalog.                                                                  |
| `request_iceberg_sync` | `connection`, `target`, `schema`, `table` (both optional) | Opens the question of [Bringing a sync up to date](iceberg.md#bringing-a-sync-up-to-date) in VS Code, marked as asked by an assistant, for the lake, a schema or a table that was synced to the target before. Nothing is written unless you confirm it there. The call waits for your answer and the sync, and returns what came of it: `synced` (with the snapshot, the tables written and those that failed), `nothing`, `declined`, `cancelled`, `failed`, or `uncovered` when nothing of it was synced to the target before: a first sync starts in the explorer. |

The connection must be connected in the explorer; a target is named as the row of the tree names it, without `Iceberg ·`. `request_iceberg_sync` is marked as a tool that writes (`readOnlyHint` false, `destructiveHint` true), so a client may ask before it calls it; your yes in VS Code is what writes. The sync reads the snapshot that the explorer shows, as **Sync to Iceberg...** does.

## Prompts and notes

The server offers three prompts, which clients show as slash commands:

| Prompt             | Arguments                                                     | Asks the assistant to                                                                                                                                        |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `why_is_this_slow` | `connection`, `target` (a view or table, or a statement)      | Read the object, run `explain_analyze` and `profile`, read the statistics of the scanned tables and the maintenance advice, and name the causes and changes. |
| `optimize_query`   | `connection`, `sql`                                           | Analyze and profile the statement, propose a faster one that returns the same rows, check it with `explain`, compare, and open it with `open_sql`.           |
| `extend_view`      | `connection`, `view` (`schema.name`), `wish` (what to change) | Read the view and what it reads, write `CREATE OR REPLACE VIEW`, check its `SELECT` with `explain`, name the views that change with it, and open the script. |

The resource `aantje://notes/duckdb-ducklake-sql` holds notes on DuckDB and DuckLake SQL that assistants often get wrong: `LIMIT` instead of `TOP`, quoting, time travel with `AT (VERSION => n)` and the alias before `AT`, `table_changes`, and the functions of the DuckLake extension with their parameters, from the vocabulary of the SQL editor.

## Errors

A connection that the explorer has not connected answers that it has to be connected first; a name that is unknown or ambiguous answers which. A failure of aantje (a catalog that cannot be read, a query that ends) answers with aantje's message, as a notification would show it; an unexpected error answers that reading failed and leaves the details to the output channel. Secrets that aantje knows are masked in every error answer. A cancel of the client stops the reads that can be stopped.

## Log

The output channel of aantje logs the start and stop of the server, the window files of other windows it removed, every `initialize` (the client and the protocol it asks for), every refused request with its reason, and every tool call: the tool, the connection as the client named it, the statement (its first 200 characters on one line), the duration, and the size of the result or the error. An unexpected error goes to the log with its causes. The logger masks secrets as everywhere ([Logging](logging.md)). Requests and methods are logged at the level Debug. aantje shows nothing else of what the assistant runs: no results panel, no Query History entry.

## Security

The server answers only on `127.0.0.1`, only with the token of its start (compared in constant time), only to a `Host` of this machine with its port, never to a request with an `Origin` (a web page), and takes at most 1 MB per request. What the tools return goes to the provider of the assistant's model: metadata, plans and profiles with the literals of the statement, statistics with minimum and maximum, and rows only when you allow them. See [Security](security.md#the-mcp-server).

## Known limits

- The tools read what the explorer has open; a connection must be connected in the explorer first.
- The columns of a view are not listed: DuckDB resolves them by running the SQL of the view. `describe_object` gives the SQL; `explain` of `SELECT * FROM` the view binds it.
- `describe_object` gives the comments of top-level columns; a comment on a nested field is not listed.
- `explain` takes only statements that read: the session attaches the lake read-only, where DuckDB cannot plan a change.
- The plans and profiles are DuckDB's JSON as it is; aantje draws nothing of them.
- `request_iceberg_sync` brings syncs up to date; a first sync to a target, and the choice of its namespace and partitioning, start in the explorer.
